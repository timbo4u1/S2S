# S2S Value Validation Protocol

**Purpose:** determine whether S2S produces actionable data-quality information and whether its selection rules improve downstream use of motion data beyond simpler baselines.

This is a pre-run protocol, not a claim that the tests below have already passed.

## Current evidence and limits

The committed PAMAP2 Level 4 experiment uses leave-one-subject-out (LOSO) evaluation on 9 subjects, 14,256 windows, and three random seeds (42, 43, 44). The current four-condition comparison reports:

- Three IMUs vs. chest-only (B−A): +4.41 percentage points mean paired per-subject fixed 12-class macro-F1.
- Chain-filtered vs. unfiltered three-IMU training (C−B): +0.02 pp mean across seeds, with both positive and negative seed results.
- Tier-weighted vs. chain-filtered (D−C): +0.25 pp mean across seeds.

These are exploratory results. The three seeds repeat the same nine subjects and **must not be counted as 27 independent subjects**. They support an observed sensor-fusion benefit for this dataset/model setup; they do not establish that chain filtering improves downstream classification.

## Experiment 1 — Controlled downstream utility

Use the `experiment/pamap2-matched-retention-control` branch / PR that adds condition E before running this protocol. Do not overwrite the original committed results.

### Conditions

| Condition | Training data | What it tests |
|---|---|---|
| A | Chest IMU only; all usable training windows | Single-sensor baseline |
| B | Three IMUs; all usable training windows | Sensor-fusion effect |
| C | Three IMUs; keep windows above the chain-score threshold | Physics-based selection |
| D | C plus the configured tier weights | Tier weighting |
| E | Three IMUs; deterministic random subset matched to C by exact per-class counts and total training size | Control for reducing training volume and changing class balance |

All conditions use the same held-out subject, training-only normalization, pre-specified model configuration, and the same test windows. The chain threshold is computed only from training subjects.

### Run plan

Use the same PAMAP2 directory for all runs and store outputs under new names:

```bash
cd ~/S2S
DATA="$HOME/S2S_data/pamap2"

for seed in 42 43 44 45 46; do
  python3 experiments/level4_multisensor_fusion.py \
    --data "$DATA" \
    --cv loso \
    --seed "$seed" \
    --epochs 40 \
    --out "experiments/results_level4_pamap2_loso_matched_seed${seed}.json"
done
```

Run one repeat of seed 42 to a second filename and compare the JSON metrics and fold predictions for deterministic repeatability. Do not compare or pool old results generated by a different code version as if they were the same experiment.

### Primary comparison and reporting

The key contrast is **C−E** (`C_chain_filtered` minus `E_random_class_matched`). This holds training-set size and per-class counts constant; it therefore asks whether the particular windows selected by the chain score help more than a random selection with the same class composition.

Report:
- Mean paired per-subject macro-F1 difference and every per-subject difference.
- The spread across seeds separately from between-subject variation.
- Fixed 12-class macro-F1, supported-class macro-F1, weighted-F1, accuracy, per-class support, and the number of retained training windows.
- B−A, C−B, C−E, D−C, and E−B; do not attribute B−A improvement to S2S filtering.
- A subject-level uncertainty interval, resampling subjects as the independent units and averaging repeated seeds within each subject. With only 9 subjects, label inferential estimates as exploratory and avoid treating the seed repeats as independent data.

If C−E is near zero or negative, conclude that a downstream benefit from the chain-selection rule has **not been demonstrated** on this benchmark. Do not move thresholds or model settings after seeing held-out results and then report the same folds as a final evaluation.

## Experiment 2 — Known-corruption detection

Build an evaluation set by applying deterministic, documented corruptions to copies of real sensor windows. Preserve the clean source and record the corruption type, subject/source-window ID, random seed, parameters, and expected affected modality/law for each generated case.

Include distinct families rather than one generic “synthetic” class:

- Timestamp resets, non-monotonic timestamps, gaps, and session splices.
- Isolated spikes and bounded high-frequency/powerline interference.
- Frozen channels/sensors, sensor dropout, cross-sensor offsets, and timing shifts.
- Independent Gaussian signals and the specific OU/Cholesky variants that are actually evaluated.
- Clean biological controls, including rest/static windows, because legitimate low motion can resemble faults.

Split by subject/session before selecting thresholds. Calibrate thresholds on training subjects only and report the untouched subjects' results. Do not put overlapping windows from one source segment on both sides of a train/test split.

Compare S2S with simple baselines where appropriate: timestamp/missingness checks, amplitude limits, derivative/spike limits, and a no-detection baseline. For each corruption family, report sensitivity, specificity, false-positive rate on clean real windows, false-negative rate, assessment coverage (`PASS`/`FAIL`/`NOT_ASSESSED`), and per-law outcomes. Report the clean rest/static false-positive rate separately from active-motion false positives.

State explicitly which corruption recipes were tested. A finite test set does not prove that all synthetic generators can be detected.

## Experiment 3 — Independent replication

Recruit at least one motion-data owner or research group that did not develop S2S.

1. Let the partner select a dataset/use case and, where possible, retain control of reference labels and held-out sessions.
2. Freeze the S2S commit, configuration, thresholds, and metrics before running against the held-out evaluation data.
3. Do not tune on the partner's evaluation set. Record software version, environment, input assumptions, missing modalities, and all `NOT_ASSESSED` outcomes.
4. Have the partner review a sample of accepted and rejected windows without seeing S2S's reason first, then compare expert judgment with law-level explanations.
5. Record false alarms, missed defects, installation effort, runtime, and which explanations lead to an actionable recording or labeling decision. Publish negative findings alongside positive findings.

Agree acceptance thresholds with the partner *before* evaluating their data. One possible operational goal is a pre-agreed maximum false-rejection rate on clean, expert-reviewed windows; the appropriate limit depends on the application and cannot be chosen after results are known.

## What would count as evidence of value?

S2S has a defensible, narrow claim only when the evidence shows a repeatable, measurable outcome:

- **Quality detection:** known injected defects are identified on held-out real-source sessions, with a measured false-positive rate on clean and rest/static controls, and performance is compared with simpler checks.
- **Downstream utility:** C outperforms E under matched training size/class balance, and the per-subject result is not driven by a single subject. Otherwise, report that utility improvement was not demonstrated.
- **Independent usefulness:** an outside data owner finds the reports interpretable and takes specific action based on them.
- **Reproducibility:** the exact command, software revision, configuration, input provenance, raw results, and analysis are published.

S2S's GOLD/SILVER/BRONZE/REJECTED output is a software-defined assessment, not independent accreditation, proof of biological origin, or a safety certification. Real-time latency measurements are not worst-case execution-time guarantees. Do not claim a robot or prosthetic system is safe based on a data-quality score or the current simulation demonstrations.

## Evidence record template

For each evaluation, preserve these fields in a result report:

| Field | Required information |
|---|---|
| Code | Git commit, release, Python/versioned dependencies |
| Data | Dataset version, licenses/permissions, subject/session split, sampling rates, modalities |
| Config | Window size/stride, thresholds, model hyperparameters, random seeds |
| Coverage | Windows assessed and not assessed, by modality and law |
| Detection | Per-corruption sensitivity/false positives/false negatives and clean-control false rejection |
| Utility | Fold-level predictions, per-subject metrics, matched-control comparisons |
| Reproducibility | Exact command, output JSON, rerun comparison |
| Limitations | Missing inputs, unsupported cases, warnings, exclusions, failures |
